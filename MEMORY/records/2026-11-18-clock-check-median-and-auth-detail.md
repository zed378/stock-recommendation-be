# Clock check by median, and the key-test message names the refusal (2026-11-18)

Two errors appeared when the owner tested an Indodax key from the UI: `CLOCK_SKEW`, then `AUTH`.

**CLOCK_SKEW was a false positive.** The VM clock is NTP-synced (offset about +7 ms). From the VM, `GET indodax.com/api/server_time` read within 50 ms of the host clock in most of 12 readings, but two came back about 0.8 to 1 s off (the endpoint is served through caches) and one 177 ms off. The check used one reading against the 250 ms limit (ADR-041), so one stale reading halted. Change in `connector/client.py` `check_clock`: the offset is the median of 5 readings, and a median beyond the limit is measured once more after 0.5 s before it counts (the documented "re-sync, retry once, then halt", `docs/06/08`). The 250 ms limit is unchanged; a clock that really is off moves every reading and still halts. Cost: 5 `server_time` requests per check instead of 1 (the check runs at most once a minute).

**AUTH is not diagnosed.** The UI showed only the class. `check_account` now reports the class, the exchange's numeric code and the HTTP status, for example `(AUTH, code -1022, HTTP 400)`; a non-numeric code is dropped and the exchange's own text is never shown. `-1002` (401) means invalid credentials (wrong key or secret, or not a Trade API 2.0 key); `-1022` (400) means a bad signature or nonce, which would point at our signing (still never observed against the real exchange, T2-07). `-2015` would be a permission or source-IP problem and is a different class.

Tests: two new clock tests (a stale minority does not halt; stale twice in a row does; one bad measurement is re-measured), two for the message, a changed assertion (5 `server_time` requests, not 1). Two tests that assumed one request per clock check were corrected: the soak test now measures simulated minutes from the mock clock instead of assuming 11 s per cycle, and the sustained-outage test moves the reconciler's timer out of the way (the throttle's waits advance the mock clock, which let the reconciler halt first). `test_credential_admin` had a throttle whose sleep did nothing on a frozen clock, which hung with more than one request; its sleep now advances the mock clock.

Not verified: any signed request against the real exchange; whether the stale readings still occur in the same proportion; the real cause of the AUTH refusal.

## Correction the same day: median was the wrong estimator (measured in the container)

After the median-of-5 image `06ebac0` was deployed the Trader made 10 `server_time` requests per 11 s cycle: both measurements failed every cycle. Measured inside the Trader container over one reused connection (12 readings): offsets were either about -28 ms (fresh, round trip about 60 ms) or about -764 ms (served from a cache, round trip about 10 ms), roughly half and half. So a median fails about half the time, and the earlier "one in six" estimate (12 curl readings, fresh connections) was too low.
A cache can only make the server's time older, so `server - local` from a stale reading is only ever too low: the reading closest to zero is the freshest, and a fresh reading inside the 250 ms limit proves the clock is inside it. Indodax rejects a timestamp 1 s or more *ahead* of its clock; that case makes every reading, stale or not, lower still, so it cannot pass. `check_clock` now reads up to 5 times, stops at the first reading inside the limit (usually one or two requests), otherwise uses the closest to zero, and measures once more before halting. The limit is unchanged. Tests: a fresh reading among stale ones is enough; the check stops at the first fresh reading; all readings stale twice in a row halts; one all-stale measurement is re-measured; a real 1.5 s skew still halts.
Also noticed: with the median image the Trader was halting-and-retrying its clock check every cycle (and logging the CLOCK_SKEW traceback as a failed snapshot step), which also hid whether the key test could reach the exchange. The earlier 9b52dfa image (one reading per check) very probably failed the same way, since it also sent one `server_time` request per cycle instead of one per minute.
